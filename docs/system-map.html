D1

CSV import silently corrupts EU-locale amounts

P0 · data corruption~15–20k tokens
Goal: amount parsing must never silently produce a wrong number for a supported import — parse it right, or flag it for review. Never complete silently on a bad parse.
Evidence

ClanTabKit/Sources/ClanTabKit/Import/CSVImport.swift — amount parse unconditionally strips commas before parsing. "1234,56" (EU decimal comma) becomes 123456, not 1234.56. No warning fires.

Options weighed
  • A — full locale-sniffing. Detect US vs EU formatting per file. Most "correct," but there's no real EU sample file to build it against — you'd be guessing at a spec, same mistake as building the pending-approval feature on spec instead of demand.
  • RecommendedB — narrow rule + sanity net. Only treat a comma as a EU decimal when there's no period AND exactly 2 digits follow it; otherwise keep today's thousands-separator behavior. Pair with a plausibility check per row (flag anything wildly out of line with the rest of the file) as a safety net regardless of which path parsed it.
  • C — sanity net only, skip the rule change. Cheaper, but leaves the actual EU case still silently wrong — only catches it if the bad value happens to look statistically out of place.
Steps
  1. Add a per-row plausibility check after computing amountMinor (compare against neighboring rows in the same column); on failure, surface the existing import-warning UI instead of importing silently.
  2. Fix the comma rule per option B above.
  3. Add tests: the existing Future.csv (US) fixture must still pass unchanged; add a hand-built EU-style fixture asserting the correct amountMinor.
  4. Run swift test --package-path ClanTabKit --filter CSVImport yourself before calling this done — don't just claim "make check green."
